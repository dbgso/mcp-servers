## 設計を作り直した経緯

**初版は「headless でレイアウト → SVG を自前生成」という構成で実装を完了していた**（1,899 行 + テスト 1,517 行、カバレッジ 99.6%）。動作もしていた。それを破棄して現在の HTML 専用構成に作り直している。

理由は、初期要件が「人間がグラフィカルに見たい」であり、それにはページで足りたため。静的 SVG のために払っていたコストは:

- `svg/geometry.ts`（境界クリップ・矢印・自己ループ・平行辺）211 行
- `svg/render.ts`（SVG 生成）306 行
- `measure.ts`（canvas がないためのラベル幅推定）225 行
- 対応するテスト 686 行

`measure.ts` が必要だったのは、**headless には canvas がなく文字幅を測れない**ため。ブラウザに任せればこの問題自体が消える。

この判断はユーザーの「html を生成してくれるというだけでも別に良かった」という指摘で確定した。計画段階で「出力3形式は全部入れる、パラメータ化できるので議論しない」と決めていたのが誤りで、出力形式を1つ増やすのは設定値ではなく 700 行超の実装だった。実装量が大きく変わる分岐を「パラメータだから」と片付けてしまっていた。

### 破棄した実装から得た知見（headless 特有の落とし穴）

現構成では不要になったが、headless で cytoscape を使う場合には有効。

| 落とし穴 | 症状 |
|---|---|
| `cy.width()/height()` が headless で 0 | `breadthfirst` の座標が `a(-4.375e+49, 0)` になる。`boundingBox` の明示で解消 |
| cytoscape は結果を `boundingBox` にリスケールする | dagre / cose に渡すと計算済みの間隔が上書きされノードが重なる。**面積ベースのレイアウトにのみ渡す** |
| 要素定義の `position` が読み戻されない | `preset` が全ノードを原点に積む。`positions` オプションで直接渡す |
| cytoscape インスタンスがハンドルを保持 | `cy.destroy()` を呼ばないと Node プロセスが終了しない |

2番目は実データを描画して初めて発覚した。実測（孤立ノード6件、dagre LR）:

| | y 座標 |
|---|---|
| boundingBox あり | 0, 133, 267, 400, 533, 667 — 800 を正確に6等分（＝リスケール）。高さ56のノードが重なる |
| boundingBox なし | 19, 106, 193, 280, 367, 454 — 87px 間隔。`nodeSep` が生きている |

3番目は現構成でも該当するため、`preset` の座標は `positions` で渡している。

## レビュー指摘への対応: レイアウトの多態化とディレクトリ構成

初版はレイアウトごとの差異を if 連鎖で書いていた。`coding-rules__polymorphism` の "Branching by type" そのものだった。

```ts
// 修正前 (layout-spec.ts)
if (name === "dagre")        { return { ...base, rankDir, nodeSep, rankSep, edgeSep }; }
if (name === "breadthfirst") { return { ...base, directed: true, grid: true }; }
if (name === "cose")         { return { ...base, nodeRepulsion, idealEdgeLength, numIter }; }

// 修正前 (html.ts) — レイアウト固有の知識がレンダラに漏れていた
const dagreScripts = layoutSpec.name === "dagre" ? dagreUrls.map(...) : "";
```

さらにレイアウト名の一覧が**3箇所**に散っていた（`types.ts` の union / `errors.ts` の `LAYOUT_NAMES` / `layout-spec.ts` の if 連鎖）。レイアウトを1つ足すと4ファイルを触る必要があり、ルールの「新しい状態を追加しても呼び出し側の変更が不要」を満たしていなかった。

`Layout` インターフェースと `layouts/` レジストリに置き換えた。名前の一覧は `LAYOUTS: Record<LayoutName, Layout>` の型だけが持つ。

また `html.ts` をトップレベルに平置きしていたが、これは**出力形式の1つ**にすぎない。`renderers/html/` に移し、将来2つ目を横に並べられる構成にした。`escape.ts` は HTML 固有なので同じ配下に移した。

### 退行を防ぐテスト

「`layouts/` の外でレイアウト名と比較していない」ことを、ソースを走査して機械的に検査している。将来また if 連鎖が生えたら落ちる。

### 再検証

## レビュー指摘への対応 (2): Renderer インターフェース

`renderers/html/` というディレクトリ名で「出力形式の1つ」と約束しておきながら、`Renderer` 型は存在せず、実体は `renderHtml` という単なる関数だった。名前だけの約束になっていた。

当初、私は「実装が1つで分岐も無いのだから抽象は不要（`Dialect` は実装が3つあるから意味がある）」と判断した。これは**2点で誤りだった**。

1. `RenderGraphHtmlParams` に「どのレンダラにも要るもの（graph / layout / theme / title / legend）」と「HTML 固有のもの（cytoscapeUrl / layoutScriptUrls）」が混ざっていた。インターフェースを切るとこの分離が強制される。**レンダラが1つでも意味がある**
2. より重要な点として、ユーザーの指摘: **型を切っておかないと、2個目が来たときにも抽象化されない**。次に触るのがエージェントである場合、既存の構造にパターンマッチするので、インターフェースがあれば実装し、無ければまた単独の関数を書く

2 についてはこのセッション自体が実例になっている。`renderers/html/` という名前を付けた当人（私）が中身の契約を作らず、レイアウトの if 連鎖にも指摘されるまで気づかなかった。

### 反論として出した点と、その扱い

「型は名前を付けたものしか縛らない」— `Renderer<SvgParams>` を満たしたまま共通パイプライン（`prepareGraph` / `resolveLayout`）を再実装することは可能であり、ガードレールとしては薄い。

またパターンマッチは逆向きにも働く。1実装から決めた型は次の実装を**歪める**方向にも作用する（公開型の変更は破壊的変更に見えるので、広げるより合わせに行く）。

ただし非対称であり、結論は覆らない。型がズレていれば2個目が歪んでレビューで見えるが、型が無ければ2個目は無関係な別実装になり**継ぎ目自体が存在しない**ため気づけない。

この反論に対処するため、**レイアウトと同じ機械検査**を追加した。`renderers/*/` を走査し、各ディレクトリのエントリポイントが `Renderer` を満たすオブジェクトを1つ export していることを検査する。2個目が「継ぎ目の横に素の関数として」現れると落ちる。型だけでは捕まえられない部分をテストで補っている。

### 戻り値を型引数にした理由

`render(params): string` と決め打つと、ラスタ形式（`Uint8Array`）と非同期レンダラ（`Promise`）で必ず壊れる。`Renderer<TParams, TOutput = string>` にしてあるので、どちらも既存の呼び出しを変えずに入る。

## レビュー指摘への対応 (3): 共通型で呼べない設計は多態ではない

`Renderer<TParams extends RenderParams, TOutput>` として、HTML 固有の `cytoscapeUrl` / `layoutScriptUrls` を `RenderGraphHtmlParams` に入れ、それを `render` の引数型にしていた。

この形だと、形式を知らない呼び出し側は `Renderer<RenderParams>` としてしか持てず、固有設定を渡す術がない。resolver 経由では型が潰れる、と当初「パターンA の利点」として説明したが、**それは利点ではなく設計の欠陥だった**。共通型で呼べないなら多態になっていない。

原因は責務の取り違えで、`cytoscapeUrl` は**レンダラの設定**であって**render の引数**ではない。

```ts
// 修正後
interface Renderer<TOutput = string> {
  readonly format: string;
  render: (params: RenderParams) => TOutput;   // 引数は共通型だけ
}

export class HtmlRenderer implements Renderer {
  readonly format = "html";
  constructor(private readonly options: HtmlRendererOptions = {}) {}
  render = (params: RenderParams): string => renderHtml({ ...params, ...this.options });
}
```

**形式ごとに違う部分はコンストラクタで決め、`render` はどの形式でも同じ呼び出しにする。** これが多態の定石であり、実装をクラスで与えるのはコンストラクタが「違いを吸収する場所」として構文上はっきりするため。`coding-rules__polymorphism` の Good Example もクラスで書かれている（当初これをオブジェクトリテラルで実装していたのは、ルール文書の読み落とし）。

型で検証した結果:

| | 結果 |
|---|---|
| `Record<string, Renderer>` に入れる | ✅ |
| 共通型のまま `render({ graph, title, layout })` | ✅ |
| 固有設定を構築時に束縛 | ✅ |
| 固有設定を `render` に渡す | ❌ `TS2353`（設計どおり弾く） |

なお `render` はメソッド構文からプロパティ構文に変えた。メソッド構文は双変で、`RenderParams` より多くを要求するレンダラが共通型の入れ物を素通りしてしまう（実測で確認）。プロパティ構文なら `TS2322` で弾かれる。

`renderGraphHtml` は引き続き両方を受ける。HTML と分かっていて `Renderer` を経由しない呼び出し側のための入口。
