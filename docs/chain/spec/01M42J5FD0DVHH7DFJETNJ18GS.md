# 報告構造の仕様

要求「AI の報告を、事前定義した構造から HTML として配送する」の、報告の項目と必須条件を規定する。

## 読みやすい報告の基準

項目より先に基準を置く（`policy__criterion-before-detection`）。

各基準は観測した失敗から来ている。R1〜R6 は issue #84、R7〜R11 はこのツールで書いた報告で観測した。R12 と R13 は、R11 で観測した失敗が同じ形の項目でも起こるため広げたもの。

| # | 基準 | 観測した失敗 |
|---|---|---|
| R1 | 結論が先頭にある | 作業した順（経緯 → 失敗 → 修正）に書いた |
| R2 | 1項目に事実は1つ | 1文に事実2つと帰結1つを詰めた |
| R3 | 主張には生の根拠が付く | 測定結果を貼らず、自分の言葉で言い換えた |
| R4 | 読み手に求めることが分かれている | 判断してほしいことが本文に埋もれた |
| R5 | 本題と脇道が別の階層にある | 聞かれていない発見を本題と並べた |
| R6 | 訂正は訂正として示す | 前の説明が誤っていたことを言わずに上書きした |
| R7 | なぜその作業をしたかが分かる | 作業のきっかけを書かず、読み手が対応の理由を読み取れなかった |
| R8 | 自分で決めたことは、退けた候補と理由とともに示す | 修正方針だけを書き、他の候補と選んだ根拠を読み手が確かめられなかった |
| R9 | 候補の比較は、候補ごとの長所と短所を並べた表で示す | 候補を箇条書きで並べ、長所と短所を見比べられなかった |
| R10 | 対応しなかった場合の影響と、対応した場合の影響範囲が分かる | 何を直したかだけを書き、放置した場合の害と、変更が何に及ぶかを読み手が判断できなかった |
| R11 | 影響は 5W1H（誰が・何が・いつ・どこで・なぜ・どうすれば）で示す | 影響範囲を「対象 / 影響」の2列で書き、誰がいつ何をすればよいか読み取れなかった |
| R12 | 誰かが動く作業（読み手に頼む作業、書き手に残る作業）も 5W1H で示す | R11 と同じ形。作業を「何を」だけで書くと、誰がいつまでにどこでどうやるかが抜ける |
| R13 | 変更と脇道の発見は、どこのことかを示す | R11 と同じ形。場所のない変更や発見は、読み手が確かめに行けない |

通じたのは `npm pack` の出力をそのまま貼ったときだけだった。R3 がこの仕様の核である。

## 項目

AI はこの構造の値だけを渡す。散文の段落も HTML も書かない。

### 必須

| 項目 | 型 | 中身 | 基準 |
|---|---|---|---|
| `title` | string | 何の報告か | — |
| `conclusion` | string | 何が終わったか、または何を判断してほしいか | R1 |
| `background` | string | 作業のきっかけ。誰に何を頼まれたか、何に気づいたか | R7 |
| `impact.ifLeft` | string | 対応しなかった場合に何が起きるか | R10 |
| `impact.scope[]` | 1件以上 | 対応した場合に影響が及ぶもの1件ずつ。下の 5W1H をすべて埋める | R10, R11 |
| `impact.scope[].who` | string | 誰が（影響を受ける人・もの） | R11 |
| `impact.scope[].what` | string | 何が変わるか | R11 |
| `impact.scope[].when` | string | いつから（例: PR のマージ後、次のリリース） | R11 |
| `impact.scope[].where` | string | どこで（ファイル、ツール、画面など） | R11 |
| `impact.scope[].why` | string | なぜそうなるか | R11 |
| `impact.scope[].how` | string | 影響を受ける側はどうすればよいか | R11 |
| `claims[]` | 1件以上 | 結論を支える主張 | R2, R3 |
| `claims[].statement` | string | 主張1つ | R2 |
| `claims[].evidence[]` | 1件以上 | 主張を支える実行結果 | R3 |
| `claims[].evidence[].source` | string | 何を実行したか（コマンド、ファイル、URL） | R3 |
| `claims[].evidence[].output` | string | 実行結果そのもの。要約しない | R3 |
| `asks[]` | 0件以上 | 読み手に求めること。空なら「対応不要」と表示する | R4 |
| `asks[].kind` | `decision` \| `action` | 判断か、作業か | R4 |
| `asks[].what` | string | 求めること1つ | R2, R4 |
| `asks[].who` | `action` のとき必須 | 誰がやるか | R12 |
| `asks[].when` | `action` のとき必須 | いつまでに（例: #99 のマージ前） | R12 |
| `asks[].where` | `action` のとき必須 | どこで（ファイル、ツール、画面など） | R12 |
| `asks[].why` | `action` のとき必須 | なぜ必要か。やらないと何が止まるか | R12 |
| `asks[].how` | `action` のとき必須 | どうやるか（手順、コマンド） | R12 |
| `asks[].options[]` | `decision` のとき2件以上 | `label` / `pros`（長所）/ `cons`（短所） | R4, R9 |
| `asks[].recommendation` | `decision` のとき必須 | 推奨する `label` と理由 | R4 |
| `decisions[]` | 0件以上 | 書き手が自分で決めたこと。空なら「なし」と表示する | R8 |
| `decisions[].what` | string | 何を決めたか | R8 |
| `decisions[].options[]` | 2件以上 | 検討した候補。`label` / `pros`（長所）/ `cons`（短所）。選んだものも含める | R8, R9 |
| `decisions[].chosen` | 必須 | 選んだ `label` と、なぜそれを選んだか（`reason`） | R8 |

`asks[].recommendation.label` と `decisions[].chosen.label` は、同じ項目の `options[].label` のどれかでなければならない。

`asks` と `decisions` は空でもよいが、省略はできない。「何も求めない」「自分では何も決めていない」ことも明示させる。

### 任意

| 項目 | 中身 | 基準 |
|---|---|---|
| `corrections[]` | `said`（前に言ったこと）/ `actually`（実際）/ `why`（なぜ誤ったか） | R6 |
| `changes[]` | `what` / `where`（どこを変えたか）/ `before` / `after` | R2, R13 |
| `remaining[]` | AI 側に残っている作業。`who`（誰が持つか）/ `what`（何を）/ `when`（いつ終わるか、何を待っているか）/ `where`（どこで）/ `why`（なぜ残っているか）/ `how`（どう進めるか） | R4, R12 |
| `asides[]` | 本題ではない発見。`note` / `where`（どこで見つけたか）/ `cost`（放置した場合の影響） | R5, R13 |

任意の項目も、渡すときは各要素の欄をすべて埋める。

### 表示の順序

構造で決まる。AI は順序を選べない。

1. `title`, `conclusion`, `background`（結論の直後に、なぜそれをしたかを置く）
2. `asks`（読み手がすることを2番目に置く）
3. `impact`（対応しなかった場合の影響と、対応した場合の影響範囲。影響範囲は 5W1H を列にした表で示す）
4. `corrections`
5. `decisions`（読み手が書き手の判断を確かめられるよう、根拠の前に置く）
6. `claims` と `evidence`
7. `changes`, `remaining`
8. `asides`（折りたたんで表示する）

`asks` の判断と `decisions` は、候補を行、長所・短所を列にした比較表で表示する。推奨または採用した行に印を付け、その理由を表のすぐ下に置く（R9）。

`asks` の作業と `remaining` は、影響範囲と同じく 5W1H を列にした表で表示する（R12）。

## 検証

- 必須項目が欠けていれば HTML を生成しない
- 構造にない項目が含まれていても HTML を生成しない。黙って捨てると、書いた側は読み手に届いたと思い込む
- 欠けている項目と余分な項目は1回の応答ですべて返す。1件ずつ差し戻さない
- 検証するのは構造だけ。文の長さや読点の数など、可読性の機械的指標は v1 では測らない（下記 Q3）

## chain との対応（参考）

chain への登録は別要求だが、項目は対応が取れる形にしておく。

| 報告の項目 | chain の型 |
|---|---|
| `asks[]`（`decision`） | `proposal`。決まったら `adr` |
| `claims[].evidence` | `implementation` / `test` の裏付け |
| `changes[]` | `spec` の差分 |

## 決定事項

2026-10-04 にユーザーが決めた。

| # | 問い | 決定 |
|---|---|---|
| Q1 | 構造は固定の1種類か、ユーザーが別の構造を定義できるか | 一旦は1種類を同梱する |
| Q2 | `claims[].evidence` を必須にするか | 必須 |
| Q3 | 文の長さなどの機械的指標を検証に入れるか | v1 では入れない。基準として書くだけにする |
| Q4 | 作業の背景を項目にするか | 必須項目 `background` として追加する。任意では抜けても止まらない |
| Q5 | チャットで聞かれて答えた「根拠と他の候補」を報告に含めるか | 含める。報告に書くべき内容がチャットにしかない状態を作らない。`decisions` を `asks` と同じく空可・省略不可で追加する |
| Q6 | 候補をどう見せるか | 必ず比較表にする。候補ごとに長所と短所を書き、なぜその選択をしたかが分かるようにする |
| Q7 | 対応の影響を報告に含めるか | 含める。対応しなかった場合の影響と、対応した場合の影響範囲を必須にする |
| Q8 | 影響範囲をどう書かせるか | 5W1H を個別の必須フィールドにする。書き手が考えなくても、欠けた要素が差し戻しで分かる |
| Q9 | 影響範囲のほかに 5W1H にするものはあるか | 誰かが動く作業（`asks` の `action` と `remaining`）を 5W1H にする。`changes` と `asides` には `where` だけ足す。判断と自分の決定は比較表、主張は根拠が役割を果たすのでそのまま |
