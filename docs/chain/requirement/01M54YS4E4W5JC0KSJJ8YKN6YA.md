# 上流で決まっていることしか下流に書けないようにする

## 背景

req / spec / design の 3 層で文書を運用していたところ、req が「原則と基準だけ」という考え方から
外れていった。約 300 件の項目を分けると、原則 13、基準 129 に対して、守り方の具体 39、重複 64、
例外 8 が req に入っていた。決まりは markdown に書いてあり、書く側 (人も AI も) が毎回それを
守れるとは限らない。見直しも、読む人の判断で揺れる分類に頼るしかなかった。

AI を使った開発の精度を上げるには、次のどちらかが要る。

1. AI への入力を入念に練り、設計に時間を使う
2. まず作り、間違いを見つけたら必ず根本 (上流) から直し、古い実装を 1 か所も残さない

どちらも、層ごとに書くべき粒度を間違えないことと、変更が必ず上流から伝わることを前提にしている。

## 要求

1. **下流には、上流で決まっていることしか書けない。** 書けるかどうかは、文の中身ではなく、
   上流の決まりを指せるかどうかで決まる。
2. **書けないときは、上流の情報が足りないことが記録として残る。** その記録は、上流に何を足せば
   書けるようになるかを言う。
3. **上流が足されたら、それによって書けるようになった下流が分かる。** 最初に書けなかったもの
   だけでなく、同じ上流で決められる他のものも含めて。
4. **上流が変わったら、その上流を前提にした下流がすべて分かる。** 直し漏れが 1 か所も残らない
   ように。
5. **判定は機械で決まる。** 同じ入力に同じ答えを返し、AI が操作している最中にも、CI でも
   同じ判定を使える。

## 対象外

- 文の中身の意味を判定すること (原則か守り方か、など)。判定は id と参照の型で行う。
- 文書の作成・承認 (interactive-instruction-mcp の役割)。
